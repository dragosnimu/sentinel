# Sentinel

Autonomous cybersecurity agent for a single internet-facing Linux server.

Sentinel watches the traffic and logs of every internet-exposed application on
the host, detects intrusion attempts, blocks attackers through nftables,
scans installed packages and application source code for vulnerabilities,
generates *safe* patch procedures (with backup, health checks and automatic
rollback), reports everything to a web dashboard, and talks to the operator
over Telegram in real time.

Standalone: it depends on nothing but the host it runs on, and it does not take
ports 80 or 443 — the dashboard serves on its own port (8443 by default), so a
host that is already a web server stays one.

Target environment: **AlmaLinux 9**, native systemd, Python 3.12.

Interface language is Romanian; code and docs-for-code are English.

---

## What it does

| Capability | How |
|---|---|
| Traffic & intrusion monitoring | Suricata (IDS mode, BPF-filtered) + journald/sshd/nginx/auditd collectors → normalized events |
| Intrusion detection | Deterministic signature, threshold and statistical-baseline rules; per-actor kill-chain state machine |
| Attack prediction | Empirical kill-chain transition probabilities from the host's own history, crossed with known open vulnerabilities on the probed asset |
| IP blocking | `nftables` table `inet sentinel`, named sets with kernel-side TTL, `policy accept` (deny-lister, never a default-deny firewall) |
| Vulnerability scanning | `dnf updateinfo --security`, Trivy (image/fs/SCA/secrets/misconfig), pip-audit / npm audit / composer audit, nuclei (DAST), semgrep (opt-in), Lynis, plus built-in web & TLS checks |
| Safe patching | Schema-validated patch plans generated by Claude, deterministically safety-checked, executed step-by-step with backup + health checks + auto-rollback |
| Alerting & control | Dedicated Telegram bot, long polling, inline buttons, two-step confirmation on destructive actions |
| Reporting & analytics | FastAPI + Jinja2 + HTMX dashboard behind nginx/TLS: incidents, actors, vulnerabilities, patches, service availability & capacity history |

## Architecture in one picture

```
 internet ─▶ nginx :8443 ─▶ 127.0.0.1:8787  sentinel-web
                                        │
 eth0 ─▶ suricata ─▶ eve.json ──┐       ▼
 journald / nginx / auditd ─────┼─▶ sentinel-ingest ─▶ PostgreSQL ─▶ sentinel-detect
 docker events ─────────────────┘                                        │
                                                       ┌─────────────────┴────────────┐
                                                       ▼                              ▼
                                              sentinel-ai (Claude)          auto-block decision
                                                                                      │
                                                            sentinel-executor [root] ─┘
                                                                      ▼
                                                       nftables  table inet sentinel
```

Everything durable goes through PostgreSQL. There is no message broker.
Privileged actions go through one small root daemon over a unix socket; the
web process can never reach it.

## Ports

| Port | Bound to | What |
|---|---|---|
| `8443/tcp` | public | Dashboard (nginx, TLS). Configurable with `--web-port` |
| `8787/tcp` | `127.0.0.1` | The app (uvicorn) |
| `5432/tcp` | `127.0.0.1` | PostgreSQL |

**Sentinel never binds 80 or 443.** A monitoring agent that displaces the service
it monitors has inverted its purpose. There are two ways to be reachable, chosen
with `--nginx-mode`:

**`dedicated`** (default) — nginx listener of Sentinel's own on `:8443`. Touches
nothing that already exists, and works whatever owns 80/443. The costs:

- The dashboard URL carries the port: `https://sentinel.example.com:8443`, and
  there is no HTTP→HTTPS redirect, because Sentinel does not own `:80`.
- `certbot --nginx` cannot be used: HTTP-01 needs `:80`. The installer obtains a
  certificate through a webroot served by whatever *does* own `:80`, or through a
  DNS-01 challenge, and falls back to self-signed rather than failing the install.
- The port must also be open in the provider's firewall — nftables on the host is
  a deny-lister with `policy accept` and does not block it, but a cloud security
  group will.

**`shared`** — a vhost on the nginx that already serves 80/443, selected by
`server_name`. Clean URL, redirect included, no new ports, and ACME works
first try because the vhost serves the challenge itself. Requires that nginx (not
Apache or Caddy) owns those ports, and writes into `/etc/nginx/conf.d/`, a
directory shared with your sites — so the installer runs `nginx -t` before and
after, and **removes its own files if the test fails**.

Both are supported and tested. See [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) §2.1
for the comparison and [docs/SECURITATE.md](docs/SECURITATE.md) §4 for what
`shared` changes about the exposure.

## Quick start

1. **Prepare secrets locally** (never committed, never in argv):

   ```bash
   ./scripts/secrets-init.sh
   ```

2. **Dry run** — preflight only, changes nothing on the server:

   ```bash
   ./scripts/deploy.sh --host 203.0.113.10 --user deploy \
       --key ~/.ssh/sentinel_deploy --domain sentinel.exemplu.ro \
       --web-port 8443 --dry-run
   ```

3. **Deploy** (open a second SSH session first — see the warning the script prints):

   ```bash
   ./scripts/deploy.sh --host 203.0.113.10 --user deploy \
       --key ~/.ssh/sentinel_deploy --domain sentinel.exemplu.ro --web-port 8443
   ```

   If nginx already owns 80/443 — the dry run tells you — the simpler option is a
   vhost on it, which also makes the certificate work without any manual step:

   ```bash
   ./scripts/deploy.sh --host 203.0.113.10 --user deploy \
       --key ~/.ssh/sentinel_deploy --domain sentinel.exemplu.ro --nginx-mode shared
   ```

   From PowerShell, use `scripts\deploy.ps1` with the same flags (`-NginxMode shared`).

Full instructions, including the Telegram bot setup and the TOTP enrolment:
**[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)** (Romanian).

## Safety properties worth knowing before you run it

- The nftables base chain is `policy accept`. Sentinel is a deny-lister. It
  cannot lock you out by *failing* — only by explicitly blocking you.
- Blocks are **not** persisted across reboot. Rebooting is always a way out.
- `touch /etc/sentinel/PANIC` flushes the entire blocklist within 60 seconds,
  via a root watchdog timer that runs independently of the main daemons.
- Auto-blocking ships **disabled**. The first 72 hours are observe-only: you
  get a Telegram message saying what *would* have been blocked, with a button.
- Patch plans are never applied automatically. Generation is automatic;
  application requires two explicit confirmations over Telegram.
- The patch validator rejects any plan touching `/opt/sentinel`,
  `/etc/sentinel`, `/root/.ssh`, `sshd_config`, `firewalld`, anything listed in
  `patch.extra_protected_paths`, and any command that is not `argv` from a
  fixed binary allowlist.
- `shell=True` and `os.system` are banned repo-wide and enforced by a test.

## Status

Delivered in phases, each verified on a live server before the next began.
**487 automated tests**, 31 of which assert that something dangerous is
*refused* rather than that something works.

| Phase | What it added | State |
|---|---|---|
| P0 | Scaffolding, plan schema + validator, skill, deployment tooling | done |
| P1 | HTTPS dashboard, Argon2id + TOTP, sessions, anti-lockout watchdog | done |
| P2 | Asset inventory, health probing, availability history | done |
| P3 | Ingestion: journald (sshd, sudo/su), nginx, auditd, geo/ASN enrichment | done |
| P4 | Detection rules, incidents, Telegram alerts | done |
| P5 | Response: nftables blocklist, one-tap block, `/panic`, hash-chained audit | done |
| P6 | Auto-block decider (observe/armed), seasonal baselines, Suricata IDS | done |
| P7 | Vulnerability scanning: `dnf updateinfo`, CISA KEV mirror, prioritisation | done |
| P8 | AI triage with a hard token budget and prompt-injection containment | done |
| P9 | Patch pipeline: plan generation, two-stage approval, verified backups, auto-rollback | done |
| P10 | Extended analytics, final hardening, full operator documentation | pending |

**Auto-block ships disabled.** The machinery is complete and tested, but the
first days are meant to be observe-only — you get told what *would* have been
blocked, with a button, so the false positives surface before anything is cut
off at 3 a.m. Patch plans are generated automatically; applying one always
takes two explicit confirmations.

Known gaps, stated rather than hidden: container logs are not collected (only
the host's), there is no dedicated file-integrity monitor beyond what auditd
covers, and the `http`/`tcp`/`docker` patch-plan check kinds are declared but
not yet implemented in the runner.
