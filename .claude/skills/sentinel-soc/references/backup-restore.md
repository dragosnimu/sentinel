# Backup and restore, per stack

How to write the `backup` section of a patch plan so that the restore actually
works. The single most common way a patch goes badly is a backup that covered
the files but not the state.

**Rule of thumb: back up everything the application would need to be rebuilt on
an empty machine — code, configuration, data, and the exact version pins.**

---

## Where backups live

```
/var/backups/sentinel/<restore_point_id>/
├── manifest.json      every item: kind, source, artifact, size, sha256, restore_argv
├── restore.sh         standalone. Runs with Sentinel completely stopped.
├── <artifact>.tar.zst
├── <artifact>.sql.zst
└── ...
```

`restore.sh` is generated by the runner from your `restore_argv` entries. It is
the operator's manual escape hatch, so the restore commands you write must be
correct in isolation — no dependency on Sentinel being alive, no dependency on
the database, no environment variables that only exist inside the daemon.

Preflight always requires **3× the estimated backup size** free. Put a realistic
`estimated_size_mb` on every item; `du -sm` the source to find out rather than
guessing.

---

## `kind` reference

| `kind` | `source` is | Runner creates | Notes |
|---|---|---|---|
| `path` | A directory or file | `tar --zstd -cf <artifact> -C <parent> <basename>` | Preserves ownership and modes |
| `mysql` | `db_name` (host/port from `target.databases`) | `mysqldump --single-transaction --routines --triggers --events` piped to zstd | `--single-transaction` matters: without it InnoDB tables lock |
| `postgres` | `db_name` | `pg_dump -Fc` | Custom format; restore with `pg_restore` |
| `docker_volume` | Volume name | `tar` of the volume mountpoint with the container stopped | Stopping first is mandatory for consistency |
| `rpm_state` | Package name | Records `name-version-release.arch` | Enables an exact `dnf downgrade` |
| `git_ref` | Repo path | Records the current commit sha and any dirty files | Cheap, and the fastest rollback for source deploys |

## Per-stack recipes

### RPM / OS packages

```jsonc
{"kind": "rpm_state", "source": "nginx",
 "restore_argv": ["dnf", "-y", "downgrade", "nginx-1.20.1-14.el9"]}
{"kind": "path", "source": "/etc/nginx",
 "restore_argv": ["tar", "--zstd", "-xf", "{artifact}", "-C", "/"]}
```

Always back up the config directory alongside the package. A package update can
ship a `.rpmnew` and change defaults; if you only downgrade the package you may
not get the config back.

Verify the downgrade target actually exists before writing it into the rollback:
`dnf --showduplicates list nginx`. AlmaLinux prunes old builds, and a rollback
to a version that is no longer in any repo is not a rollback.

### PHP / WordPress

```jsonc
{"kind": "path",  "source": "/var/www/blog",
 "restore_argv": ["tar", "--zstd", "-xf", "{artifact}", "-C", "/var/www"]},
{"kind": "mysql", "source": "blog",
 "restore_argv": ["/opt/sentinel/bin/sentinel-restore-mysql", "--db", "blog", "--file", "{artifact}"]}
```

- Back up **both**. A WordPress plugin update writes to the database (options,
  schema) as well as to disk. Files alone will not roll back cleanly.
- `wp-config.php` lives in the webroot and contains credentials — it is inside
  the archive, which is why `/var/backups/sentinel` is `0700 root:root`.
- Prefer `wp plugin update foo --version=X.Y.Z` over downloading a zip. It is
  deterministic and it updates the database state correctly.
- Rollback for a plugin: `wp plugin install <slug> --version=<old> --force`,
  then restore the database dump. Files-only rollback leaves the database at the
  new schema.
- Uploads directories can be large. If `wp-content/uploads` is > 1 GB, exclude
  it and say so in `notes_ro` — a plugin update does not touch uploads, and
  archiving 40 GB of images to patch a 200 KB plugin is how you fill the disk.

### Node.js

```jsonc
{"kind": "git_ref", "source": "/opt/app",
 "restore_argv": ["git", "-C", "/opt/app", "checkout", "<sha>"]},
{"kind": "path", "source": "/opt/app/node_modules",
 "restore_argv": ["tar", "--zstd", "-xf", "{artifact}", "-C", "/opt/app"]}
```

- Use `npm ci`, never `npm install`, in the apply step. `ci` respects the
  lockfile exactly; `install` may resolve differently and silently change more
  than the one package you meant to fix.
- Back up `node_modules` only if it is small or if reinstalling requires network
  access you may not have during a rollback. Otherwise back up
  `package-lock.json` (inside the `git_ref` or as a `path` item) and rebuild.
- Check for a build step (`npm run build`, `dist/`). If the app serves built
  assets, the build output needs backing up or rebuilding, and the rollback
  needs to say which.
- If it runs under a process manager other than systemd, find out which
  (`pm2 list`, `docker ps`) — the restart command differs.

### Python

```jsonc
{"kind": "git_ref", "source": "/opt/app",
 "restore_argv": ["git", "-C", "/opt/app", "checkout", "<sha>"]},
{"kind": "path", "source": "/opt/app/venv",
 "restore_argv": ["tar", "--zstd", "-xf", "{artifact}", "-C", "/opt/app"]}
```

- Archiving the whole venv is the most reliable rollback: `pip install
  package==old` can pull different transitive dependencies than were there
  before.
- If the app has migrations (Alembic, Django), a code rollback without a
  migration rollback leaves a schema the old code cannot read. **Back up the
  database and say explicitly in `notes_ro` whether the migration is
  reversible.** If it is not, set `risk.reversible: false`.

### Docker containers

```jsonc
{"kind": "path", "source": "/opt/app/docker-compose.yml",
 "restore_argv": ["cp", "{artifact}", "/opt/app/docker-compose.yml"]},
{"kind": "docker_volume", "source": "app_data",
 "restore_argv": ["/opt/sentinel/bin/sentinel-restore-volume", "--volume", "app_data", "--file", "{artifact}"]}
```

- Pin the image by **digest**, not by tag. `image:latest` is not a rollback
  target; `image@sha256:...` is. Record the current digest with
  `docker inspect --format '{{index .RepoDigests 0}}' <container>`.
- Stop the container before archiving a volume. A live volume snapshot of a
  database is a corrupt database.
- Never propose anything for a container whose asset is `protected: true`, or
  whose paths appear in `patch.extra_protected_paths`.

### Databases as the primary target

If the patch itself is a database engine update (MariaDB, PostgreSQL):

- `risk.blast_radius` is at minimum `multi-service`.
- `risk.reversible` is usually **false** — engine upgrades rewrite on-disk
  formats and downgrades are not supported. Say so; do not invent a rollback.
- Take a full logical dump *and* stop the service and archive the data
  directory. The dump is the portable path back; the data directory is the fast
  one.
- `maintenance_window.required: true`, always.

## Retention

Managed by `sentinel-maintenance`, not by you. For context:

- Keep the last **10** restore points, **and** anything newer than **30 days**,
  **and always the most recent successful restore point per asset** regardless
  of age (`retention_hold`).
- Never garbage-collect the only way back. If retention would leave an asset
  with zero restore points, it keeps one and logs.
- The disk guard drops the oldest *unheld* points early if free space < 15%.

## Verification

A backup nobody has restored is not a backup.

- Every artifact gets a sha256 in the manifest, checked immediately after
  creation. A checksum mismatch aborts the patch before any apply step runs.
- `restore.sh` is written but not executed at backup time.
- A **quarterly restore drill** is scheduled as a reminder. The drill restores a
  real restore point onto the canary service with all Sentinel units stopped,
  proving the manual path works when Sentinel is dead.

If asked to write a restore procedure for the operator, write it as commands
they can paste, assuming Sentinel is not running and the database is
unreachable. That is the situation in which they will actually be reading it.
